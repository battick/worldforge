## 修复：双击 start.bat 后「打开本地数据库超时」（用户真实浏览器卡死）

### 根因（用 CDP 双标签页实验逐一证实，结论都写进了 indexeddb.ts 顶部注释）
1. 不带版本号的 `indexedDB.open` 与现有同版本连接共存，永远不会被 blocked。
2. **被阻塞的「带更高版本号的 open」请求会一直排队，并把后续所有 open（含无版本号的）全部饿死**，直到占用者关闭连接。
3. **页面刷新/导航不会取消这个排队的请求**（跟着渲染进程残留）——旧版页面多次刷新会积累"僵尸"升级请求。
4. 因此"先试升级、不行就降级用旧连接"的方案根本走不通：升级请求一旦发出，本页就再也开不了新连接。
   用户浏览器里正是：旧标签页（可能被 Chrome 内存节省功能冻结）占着 v1 连接 + 历次刷新的僵尸 v2 请求 → 一切新 open 饿死 → 超时报错。

### 方案（`src/storage/indexeddb.ts` 全重写）
- `init()`：先不带版本号打开（保证数据总能读到）；版本已最新 → 直接用；版本落后 → 先用旧连接正常干活，标记 `pendingUpgrade`。
- `finishUpgrade(onBlocked)`：由 store 在数据加载完后后台调用 —— 关旧连接、发出版本升级请求，**patient 模式绝不放弃**（onblocked 只回调通知 UI，不 reject）；占用者关闭后请求自动完成，无需刷新。超时上限 10 分钟。
- store（`src/state/store.tsx`）：`pendingUpgrade / dbUpgrading / dbUpgradeError` 状态；初始化后自动启动后台升级；overlay 3 秒延迟显示（无占用时升级毫秒级完成，不闪屏）。
- App（`src/App.tsx`）：`dbUpgrading/dbUpgradeError` → 全屏指引卡（"关闭其他 WorldForge 标签页后会自动完成，无需刷新"）；初始化错误卡的提示重写（含"反复超时就完全重启浏览器"）。
- WorldOnboarding：`pendingUpgrade` 期间提示草稿暂存不可用。

### 关键教训（重要，以后别再踩）
- 验证 IndexedDB 行为别猜，直接用 CDP 开两个 target 做实验：`/json/new` 要用 **PUT**；about:blank 里 IndexedDB 被禁用，必须先导航到真实源。
- e2e 里"世界菜单项是 div 不是 button"，点击助手只搜 button，要用 evaluate 直接点。

### 验证
- `.dev/e2e-blocked-db.mjs` 重写：占用时能初始化（不转圈不报错）→ 升级等待指引卡 → 释放占用后**自动完成升级** → v2 + drafts store 就绪，8/8 通过。
- onboarding e2e 59/59、全页巡检 11/11 无回归。
- 诊断脚本（diag-*.mjs）用完已删。

## 修复：诊断日志定位到的「僵死队列 + 幽灵连接」双重卡死

用户贴回的启动日志给出了决定性线索：**不带版本的 open 请求**12 秒无任何响应
（无 blocked/success/error），而 `indexedDB.databases()` 显示 `worldforge@v1` 仍在。
→ 连接队列里堵着一个早已失效的升级请求，把所有后续 open 全饿死；页面内无法取消，
只能彻底重启浏览器进程（用户是 Edge，有「启动增强 / 关闭后继续运行后台应用」，关窗≠退出）。

### 改动
- `src/lib/diagLog.ts`：`collectPostMortem()` 改为返回结构化 `PostMortem`
  （databases/persisted/usage/quota），新增 `analyzeStall()` 判定：
  starved-queue（库存在但 open 超时）/ db-missing（连库都没有 → 隐私模式或站点数据被禁）/ unknown。
- `src/state/store.tsx`：新增 `initDiagnosis`（StoreValue），init 失败时探测并判定后一并交给 UI。
- `src/App.tsx`：错误卡按判定分三套文案 —— 僵死队列卡（标题「数据库被僵死的排队请求卡住了」，
  说明刷新无效、数据没丢含版本号、按顺序给出「关窗 → 关 Edge 启动增强/后台应用 → 任务管理器
  结束所有浏览器进程 → 重开点重试」，并按 UA 的 `Edg/` 自动切换 Edge / Chrome 专属文案）、
  数据库缺失卡、通用卡；重试按钮文案随场景变化。
- **`src/storage/indexeddb.ts` 真实 bug 修复（本次最大收获）**：`openRaw` 超时后只是 reject，
  请求仍留在队列里；占用解除后它会「迟到成功」，那条**幽灵连接永不关闭**，
  反过来把本页之后的一切升级/打开请求永久堵死（表现为：重试后卡在「正在升级数据库」）。
  现在超时路径会挂上收尾处理：迟到成功 → 立即 `close()` 并记 `idb-open:late-success`。

### 验证
- `.dev/e2e-timeout-db.mjs` 重写为**确定性双标签页**场景（原来单页注入有竞态，时好时坏）：
  标签页 A 用同源**静态资源**（`assets/index-*.js`，纯文本文档）建 v1 库 + 占住连接 + 发僵尸 v3 请求，
  再开标签页 B 加载应用 → 必被饿死。15/15 通过（含判定文案、日志内容、重试恢复、缺 store 自愈）。
  注意：`/__wf-ping` 会被 SPA 回退成 index.html，不能拿来当「同源无应用 JS」的载体。
- 回归：blocked-db 9/9、onboarding 59/59、sweep 12/12、pieces 11/11；tsc 零错误。
- 坑：两个 e2e 脚本用同一调试端口并发跑会互相串台（都连到同一个 Chrome），
  必须等前一个真正退出；`Runtime.evaluate(awaitPromise)` 没有超时，遇到永不 settle 的
  promise 会让脚本永久挂起，表达式内部要自己 `Promise.race` 加超时。

### 追加：提示泡改为「填入」而非「代发」

作者要求：提示泡点一下只**填进输入框**，用户改完觉得好再点发送。

- **填入规则**：框里是空的 → 直接填；**框里已有作者写的字 → 追加一行，不覆盖**（作者写的东西不能因为点了个提示泡就没了）。填完 `focus()` + 光标落到末尾，接着能改也能直接回车。
- 语义差异要记住：工作台的提示泡是「**摆出来的问句**」→ 追加安全；新建世界里的 `ob-suggest` 是「**候选答案**」→ 覆盖才对，所以那边（`WorldOnboarding.tsx:933`）保持原样，**不要**一起改成追加。
- **React 18 的 ref 类型坑**：`useRef<HTMLTextAreaElement | null>(null)` 会命中 `useRef<T>(initialValue: T|null): RefObject<T>` 重载，解析成 `RefObject<HTMLTextAreaElement | null>`，而 `RefObject<T>` 定义是 `{ readonly current: T | null }` —— 于是 `| null` 被套了两层，赋给 `ref={}` 直接 TS2322。**正确写法是 `useRef<HTMLTextAreaElement>(null)` + 属性类型 `React.RefObject<HTMLTextAreaElement>`**。

### 追加：修「问它话，它说完了就没下文」

作者反馈：真实模型下问它，既不弹计划卡也不执行，「说完就没了」。

**根因一（解析层静默丢动作）**：给协议解析写了体检脚本 `.dev/unit-agent-protocol.mjs`，喂真实模型的各种变形，**首轮 22 项里 11 项失败**，全是同一类 —— 动作被静默丢掉，界面上看起来就是「说完了什么都没发生」：
- `plan` 写成**对象**而不是数组（只做一件事时模型很自然的写法）→ 整个动作丢
- **根级直接给动作**（没有 say/plan 外壳）→ 动作丢且 say 为空 → 连话都没有
- 键名换成 `steps`/`actions`/`tool_calls`、参数塞进 `arguments`/`params` → 丢
- `plan` 被**序列化成字符串** → 丢
- **say 和 plan 吐成两个并列的 JSON 对象** → 拼不成一个 JSON → 整段原文当答复，**花括号直接漏在界面上**
- 根是数组、`tool` 写出 `CreateEntry`/`create-entry` 这种写法 → 也丢（后者是「未知工具」式的假失败）

修法：`protocol.ts` 重写为「只要模型表达了动作就必须救回来」（多键名别名 + 多形态归一 + 并列 JSON 分片扫描 + 占位 say），并给 `AgentReply` 加 `protocolBroken`；工具查表加 `findTool()`（去掉大小写与分隔符后再匹配）。

**根因二（提示词的口子）**：模型很爱在 `say` 里写「我先看看」，然后把 `plan` 留空 —— 按协议那等于**这件事就此结束**。原提示词没堵这个口子。现在明写：**只要打算用工具（哪怕只是查看、只是核对）就必须写进 `plan`**；只给动作不给话时补一句占位 `agent.fallback.planOnly`。

**兜底：格式没对上就自己纠正一轮**。整段散文（没给 JSON）时，老实现就此收工；现在 `useAgent` 会补一条 `agent.sys.repair` 请它重说一遍（`run.repaired` 保证每个问题**只纠一次**），界面上那一轮如实标出来（`agent.broken.hint` / `giveUp`）。

**踩到的坑（值得记）**：
- 一开始用「它在 turn 列表里是不是最后一条」决定提示措辞 → 界面先显示「这一轮就先到这里」、一秒后翻成「已请它重说一遍」，**闪烁的谎话**。改成由循环在落库时就记下实际处置（`protocolBroken: 'retried' | 'gaveUp'`），措辞一次说准。
- `send()` 里读 `document.querySelector('[data-role=agent-send]').disabled` **不是空安全的**：agent 还在跑时输入区显示的是「停下」，按钮根本不存在 → 直接抛 TypeError，把等待变成假失败。改成 `!!b && !b.disabled`。
- `unit-prompts.mjs` 收尾的 `rmSync` 在 Windows 上偶发 EPERM/EBUSY（断言早已跑完、12/12 通过），却让退出码变 1、刷出一屏堆栈 —— 改成 try/catch 并注明「下次开头还会再删一遍」。**临时目录清理失败不该影响结论。**

**验证**：`unit-agent-protocol.mjs` **22/22**（新增）；`e2e-studio-agent.mjs` 加场景 8（故意散文回复 → 如实标注 → 自动纠正 → 纠正轮给出计划卡）→ **39/39**；假上游加两个分支（`REPAIR_MARK` 识别纠正轮、关键词「散着说」故意不按格式回）。回归：sweep 13/13、e2e-i18n 全过、unit-prompts 12/12（退出码 0）、覆盖率 0 残留、tsc 0 错。

**顺手修的谎话（刷新后的计划卡）**：`turn.pending` 非空却点不动，只有「刷新/离开页面」一种来路 —— 而那个分支原先写的是「这批动作被你跳过了」。核对下来它 **100% 只会用来描述「没跳过」的情况**（跳过/执行/中止都会把 `pending` 清空），原措辞是彻底的谎。改为 `studio.agent.plan.stale`（「这批动作没有执行 —— 离开这个页面后它就作废了」），并删掉已成死文案的 `studio.agent.plan.skipped`。e2e 加场景 9（发一问 → 出计划卡 → 刷新 → 断言如实说明 + 不出现「被你跳过」+ 不再挂可点的卡）。

**又踩一个坑：假上游的调度不能看整份 transcript**。纠正轮的 `agent.sys.repair` 那句话会**留在历史里**，之后每次请求都带着它 → 假上游把它当成纠正轮反复命中，每轮都回带 plan 的答复 → 计划模式永远在等拍板 → 输入框一直禁用（看起来像应用卡死，其实是假上游调度错了）。改为**只看最后一条用户消息**（`ctx.lastUser`）—— `AGENT_RESULT_MARK` 同理，它也一直留在历史里。

**由此暴露：场景 5 之前是「蒙对」的**。它发的「库里现在有哪些条目」没命中纯问答分支（关键词是「多少/几条」），却因为历史里残留的结果回灌标记也拿到了 `plan: []`，断言照样绿。改了措辞让它真命中，并把断言从「有没有答复/有没有卡」加强为**断言答复内容**（`要我把缺口补上吗`），这样「掉进默认场景也恰好不弹卡」这类蒙混再也过不去。

**测试脚手架的三个真缺陷（都修了）**：
- 打字不能抢：输入框在 agent 跑着时是 `disabled`，而 **React 会丢弃 disabled 元素上的输入事件** → 抢着打字静默失效，后面表现为「发送键一直不可用」的假失败。`type()` 现在先等输入框可输入。
- `send()` 等待超时后仍继续点，撞空指针抛 TypeError，看不出卡在哪 → 超时抛带 DOM 状态转储的明确错误。
- 我新写的场景里那句 `await waitFor(...)` **没断言结果**，超时了也照走 —— 这才让上面那个「逻辑卡住」伪装成 TypeError。

### 追加：让 agent「会问、会来事、产出一律进审查」

作者原话：「他有时候笨笨的，比如说查不到就一直尝试查询，而不是询问用户……我说了一个不存在的条目，它能自动联想并创建新条件和写好了大纲进审查」。拆成四件事落地：

**① 会问**：新增工具 `ask_author`，**`terminal: true`** —— 执行到它这一轮即终点，后续动作标 `skipped`。它**不受三档执行边界约束**（`gated` 过滤 terminal）：要作者先批准它提一个问题本身就是荒谬的。带可选 `options`，UI 渲染成独立的 `ag-askbox`（`data-role=agent-ask*`），选项可点填入输入框。提示词明写：**零命中 = 信息不够，该问不该查**。

**② 别反复查（打转护栏）**：`useAgent` 里对每个动作按 `工具+排序后的参数` 算 `signature` 指纹；同指纹再来就拦下并标 `agent.fail.repeated`。`stalls` 累积「失败/零命中/重复」，`STALL_NUDGE=2` 时注入 `agent.sys.stuckNudge` 提醒一次；`STALL_STOP=4` 时停下并写 `turn.stuck = true`，界面用 `data-role=agent-stuck` 如实说明**为什么停**。零命中的工具结果回灌时附 `agent.sys.resultEmpty`（`ToolOutcome.empty` → `prompts.ts` 的 `renderDetail`）。

**③ 会来事 + ④ 进审查**：`create_entry`/`create_relation` 不再直接写库，改为走 `propose()` 造 `ReviewItem`（`origin:'agent'`、`rationale = ctx.why`），并落 `propose` 日志（撤销快照 `{remove:[{entity:'review', id}]}`）。`create_relation` 任一端找不到时先 `resolvePendingDraft()` 找待审草稿：两端都待审 → 拒绝；一端待审 → 把关系提议**挂到草稿 id** 上。采纳时 store 里 `acceptReview` 的 follow 逻辑改**双向匹配**（`fromEntryId === newId || toEntryId === newId`），并加**落地守卫**：两端都在库才 push 关系，否则退回驳回 + 写 `lib.state.relationEndpointMissing`。

**几处刻意的设计取舍**：
- **提问由问句本身承载，不弹计划卡**：`willAsk` 时不渲染计划卡 —— 拦一个提问等于要作者先批准它提问。

- 三档管的是「动作要不要先问」，**管不到产出要不要审** —— 即使「直接执行」档，agent 新建的条目也照旧只进审查队列。README 里专门写了一句。

### 追加：AI 干活时切页不打断 + 侧栏工作动画

作者要求：「某个页面的 ai 正在工作的时候切换其他页面也会继续工作，同时在对应的导航栏还有工作中的动画提示」。
问过范围后确认是**全部 7 处 AI 任务**（工作台 agent、资料库抽取、一致性扫描、文章审校、关系推荐、条目扩写、批量生成）。

**原先的错位（三个叠在一起，所以难查）**：AI 任务的状态住在页面的 `useState` 里，而路由切换会卸载页面。
那个 `async` 任务其实**照旧在跑**（没人取消它），但
① loading / 流式预览随卸载消失；
② 收尾的 `setResult` 打在不存在的组件上 —— **成果直接丢掉，token 白烧**；
③ 切回来组件重新初始化成 idle，`phase === 'idle'` 让输入框重新可用 → 再发一条就变成**两个循环同时改库**。

**落法**：
- `src/state/aiTasks.ts` —— 模块级任务表 `key → {navKey, worldId, phase, stream, result, error, 时间}`
  + `useSyncExternalStore` 订阅。状态活在 React 之外，卸载动不了它。
  要点：`taskOf(key)` 必须返回**稳定引用**（缺省时把 idle 记录写进表里），
  否则 `getSnapshot` 每次新建对象 → React 认为一直在变 → 无限重渲染。
  `runningNavSignature()` 返回**排序后的字符串**而不是 Set，同理。
- `src/state/agentRunner.tsx` —— 工作台 agent 的运行器挂到 `Shell` 那层（App 里包的 Provider）。
  `useAgent` 去掉 `thread` 参数，改为 `attach(threadId)`：页面只声明"我在看哪一段"。

**修的三处细节**：
1. `useAgent` 里加 `threadsRef`（每次渲染刷新）—— `send` 的依赖里没有 `store.threads`，
   闭包那份可能落后好几轮，拿它找会话会找不到。
2. **审校页用两个任务键**（`article.review` / `article.makeEntries`）。合成一个的话，

4. 资料库的分批抽取**整体放进一次 `run`**，不是每块调一次 ——

## 修「一致性检查跑完什么反应都没有」

**症状**：一致性检查点「开始审计」，转一下圈，然后只弹一句「没有发现明显的设定冲突」——
页面上什么都没有。用户原话是"什么反应都没有"。

**根因（真实、且与真模型同样复现）**：`src/ai/parse.ts` 的 `asArray` 认的是一份**硬编码键名白名单**
（`items/data/result/entries/list/results`），而每条任务的提示词早就写明了返回形状：

- 一致性检查 `{"issues": [...]}` —— **白名单里没有 `issues`**
- 关系推荐 `{"relations": [...]}` —— **白名单里也没有 `relations`**（同一个根因的第二处，一直没被发现）

于是 `{"issues": [...]}` 被 `asArray` 判成"没有列表" → 返回 `[]` →
页面走 `if (!items.length)` 分支 → 提示"没有冲突"。**整份结果被静默丢空，还长着一副成功的样子。**

为什么一直没被发现：`sweep.mjs` 只检查页面能不能渲染、**从不点按钮**；
`e2e-graph.mjs` 只测图谱的手工增删改、**从不点「AI 推荐关系」**。
假上游反倒忠实复刻了契约（`CONSISTENCY = {issues: [...]}`），所以它是能复现的 —— 只是没人点过那个按钮。

**修法（两道防线）**：
1. `asArray` 认全：`LIST_KEYS` 登记提示词里出现过的每个列表键（含 `issues`/`relations`/`categories`/`rules`/`questions`）；
   找不到既定键时，若整份返回**只有一个数组字段**就认它（模型把 `issues` 写成 `conflicts` 也救得回）；
   还容忍再包一层（`{"data": {...}}`）。有多个数组字段**不猜** —— 真歧义，猜错比返回空更糟。
2. 新增 `hasListShape()`，把「它说没问题」与「我们没读懂」分开：
   `{"issues": []}` 是结论（照常说"没有发现问题"）；`{"note": "一切自洽"}` 是答非所问 → **报错**。
   `runConsistency` / `runRelations` 走严格路径（`requireList()`），新文案 `ai.err.shapeMismatch`。

**顺带**：`parse.ts` 的注释里写死了一条约定 —— 改提示词的返回形状时，必须同时去 `LIST_KEYS` 登记。

**验证**：
- 新增 `.dev/unit-parse.mjs` **27/27**：提示词里出现过的每个列表键都要认；根级数组；
  唯一数组字段兜底；多数组不猜；既定键优先；再包一层；「空数组 ≠ 没读懂」的区分；
  以及假上游/真模型那一份真实返回能解析出问题标题。
- 新增 `.dev/e2e-consist.mjs` **30/30**：审计中按钮/侧栏动画 → 1 条问题卡（标题/说明/建议/相关条目）→
  统计与徽标 → 真的落库 → 「据此修订」生成 update-entry 并挂对 `targetEntryId` → 原问题转已处理 →
  图谱页「AI 推荐关系」进审查（`relations` 键）→ **答非所问必须报错且不塞任何东西** → 无未捕获异常。
- 假上游新增场景：世界名含「畸形返回」时返回一份「能解析、但没有列表」的 JSON（`CONSISTENCY_MALFORMED`）。

## 批量修订打磨条目

**需求**：作者原话「我希望能够批量修订打磨条目」。不是逐条进编辑器点「生成修订建议」，
而是**勾一批、一次让 AI 逐条打磨**。约束来自使用场景本身：作者要连审十几条，
所以模型必须**比单条扩写更克制**——不改的别动，别把原文整段重写让作者白审一遍。

**实现**
- **提示词**（`promptText/{zh,en}.ts` 新增 `/* 2b. 批量打磨 */` 一节）：
  `polishSystem` 里写死纪律「你正在**批量**打磨……首要纪律是**克制**……已经成立的设定一个字都不许推翻……
  确实没什么可改的就原样返回」，返回形状 `{summary, content, tags, aliases, changeNote, relations}`；
  `polishUser` 带 `{worldBrief}`/`{index}`/`{total}`/`{i}`；着力点用**平铺键**
  `polishFocusDetail/Style/Trim/Links/Conflict`（不能嵌套对象，见铁律——`promptText` 是
  `Record<PromptKey, string>`）。`src/ai/prompts.ts` 里 `POLISH_FOCUS` + `FOCUS_TEMPLATE`
  （`Record<PolishFocus, PromptKey>`，漏键 tsc 报错）+ `buildPolishPrompt()`。
- **执行**（`src/ai/tasks.ts`）：新增 `runPolish()`。顺手抽出两个**共享**函数避免两条路径漂移：
  `buildUpdateProposal()`（单条扩写与批量打磨共用，产出「条目 + diff changes」提议）与
  `relationProposals()`（找不到目标不再静默丢弃，记进 `unresolved`）。`runExpand` 改走它们。
- **全局任务进度**（`src/state/aiTasks.ts`）：`AITask` 加 `progress: {done,total,label}`，
  `setTaskProgress` 只在 `running` 时认；句柄 `useAITask` 暴露 `progress`/`setProgress`。
- **审查归组**（`src/types.ts`）：`ReviewItem` 加 `batchId?`。同一次批量的提议共用一个 id。
- **条目页批量模式**（`EntriesPage.tsx`）：勾选 / 智能挑选（`polishReasons`：正文<160 字、缺概述、
  缺标签、无关联、草稿）/ 着力点多选 / 额外要求 / 进度条 / 可停止 / 结果汇总 / 一键去审查。
  批量面板整体包在**一次** `polish.run` 里（否则侧栏那格会"转一下、停一下"）。
- **审查页**（`ReviewPage.tsx`）：抽出模块级 `missingEndCount()`；同 `batchId` 相邻项前插批头，
  提供 `acceptBatch`/`rejectBatch`（`acceptAll` 也顺手跳过被阻塞的）。
- **agent 也能做**（`src/ai/agent/tools.ts`）：新工具 `polish_entries`（`risk:'write'`，
  上限 `POLISH_MAX=8`）。`propose()` 扩展以承载 `update-entry`（`targetEntryId`/`changes`/
  `rationale` 覆盖/`batchId`）。`AgentContext` 加 `signal?: AbortSignal`，`useAgent.execute`
  构造 ctx 时传 `abortRef.current?.signal` —— 作者按停止能一路传到模型请求。`resolvePolishFocus()`
  的中文关键词表是**解析用的**（模型用中文说"补全细节"也要认），与界面语言无关，行尾 `// i18n-allow`。

**三个设计取舍**
1. **批量比单条更克制**：作者连审十几条，重写一遍的成本是成倍的。提示词把「能不动就不动」写进纪律第一条。
2. **「无需改动」是结论，「答非所问」是没读懂 —— 必须分开**（沿用一致性检查那次的教训）：
   `runPolish` 解析出的 JSON 若既没有 `content` 也没有 `summary`，抛 `ai.err.shapeMismatch`，
   **不许退化成"无需改动"**；判成"无需改动"（`changes` 为空）则**不入队**，但要记进 skipped 如实报给作者。
3. **同一目标不叠两份待审修订**：`startBatch` 先跳过已有待审 `update-entry` 的条目，避免队列里
   同一目标挂着两份互相打架的修订建议。

**踩的坑**
- **`startBatch` 忘了 `polish.setResult(summary)`**（真 bug）：`run` 只负责跑、**不代存结果**，
  所以切页回来结果卡是空的。e2e「切回来结果卡还在」把它抓了出来。教训强化见铁律 21。
- e2e 两个种子问题（非代码 bug）：对照组「余烬教团」正文太短也被智能挑选选中（补长正文）；
  厚对照「涨纪潮」没被选中，导致"判定无需改动"这条纪律没被验到（开跑前手工 `pick` 加进这一批）。

**验证**

  切页不中断 → 切回结果卡还在 → 结果计数 → 库里条目/关系一致 → 同批 `batchId` → 批头整批采纳 →
  正文真的变了 → 同目标不叠两份 → agent 也能调 → 假上游打磨分支命中。
- 假上游新增 `polish` 分支（**排在 expand 之前**判）：`polishPayload()` 看正文长度回包——
  `includes('畸形打磨')` 回一份"能解析但没有预期字段"的 JSON；正文 ≥200 字原样返回 `changeNote:''`；

## agent 的参数名：写歪了要认得出来，缺了要能照着重写

**用户报的**：让工作台 agent「把条目里提到、但还没建的人物和物品补全」，它连着调了 8 次 `read_entry`，
每次都报「**读条目 · 缺少标题**」；随后打转护栏把它停下（「它连着几步都没查到有用的东西」）。
作者的原话是「结果它根本就没补全」。

**根因（链式，三层）**
1. **工具内部只读 `args.entry`，而模型把它写在了 `title` 上。** `read_entry` 的说明只说「参数用标题或别名」，
   从没告诉过它键名叫什么 —— 它只能猜，猜成了 `title`。读不到就等于「没传」。
2. **那句报错学不到任何东西。** 「缺少标题」里既没有「你的键名我不认识」，也没有「这个工具认哪些参数名」，
   模型唯一的反应是**原样重试** —— 于是失败复制 8 次。
3. **护栏跟着给错建议。** 循环把「调用写错」和「零命中」都算成「没收获」，
   于是提醒它「停下来问作者」。可这件事压根还没开始查，问作者解决不了任何问题。

**修法（四层，各管一段）**
- **`AgentTool.args`**：每个工具声明自己认哪些参数名（31 个工具全补）。三件事共用这一份声明：
  别名归一的依据、印进工具清单给模型看、自检（`required ⊆ args`）。
- **`normalizeArgs()`**：执行前把别名折回规范名。两遍走 —— 先归位**写法**（`Entry`/`entry_id` → `entry`），
  再补**别名**（`title`→`entry`、`keyword`→`query`、中文键也认）。第二遍刻意**不抢本工具自己的另一个规范名**：
  `update_entry` 里 `title` 是「改成什么标题」，不是「改哪一个」—— 那种歧义照实报缺，不猜。
  别名是**移动**不是复制（一个原键只对应一个参数，复制会让同一件事被喂两遍）。
- **`checkRequired()`**：必填自检，报错三样齐全 —— 缺哪个 / 这个工具认哪些 / 你这次给的是什么。
- **`badCall` 标记**：`ToolOutcome` / `StepResult` 各加一位，把「调用写错」从「零命中」里分出来。
  失败回灌（`resultBadCall` vs `resultEmpty`）、护栏插话（`badCallNudge` vs `stuckNudge`）、
  停下来时的说明（`stuckBadCall` vs `stuck`）、**对话里那个短标记**（`stuckBadCallTag`）四处都分开。
- **工具清单印参数名**：`- read_entry（读）：… ｜参数：entry（必填）`。第一次就写对，比事后补救便宜得多。
- **提示词加作业指导** `agent.sys.complete`：「补全」这类活儿的顺序 —— 先读**正文**（索引里只有标题摘要，
  人名器物多半只在正文）→ 拿读到的名字去库里对（含别名、含审查队列）→ 只提真正缺的独立实体 →
  一次给齐 title/category/summary，正文给骨架 → 收尾报数，不许把「已提交审查」说成「已经建好了」。

**顺带修掉的一处界面版同款毛病**：`StudioPage` 里那个 `data-role="agent-stuck"` 标记**写死了** `agent.err.stuck`，
不管循环说的是哪一句。所以循环分得清、界面又合并回一句 —— 等于白分。
改成按 `turn.stuck: 'empty' | 'badCall'` 选标记，并且标记文字**不重复正文**（长解释在正文气泡里）。

**踩的坑**
- 假上游两轮场景不能只看 `last.includes(AGENT_RESULT_MARK)`：那句**留在历史里**，之后每轮都还带着它，
  「提议」那步会被反复命中 → 看起来像应用卡在重复同一个动作。改成按「回灌过几轮」分步。
- 后台起假上游不能用 `( ... &)`：那个 Bash 调用一结束，子进程就被回收了（表现为「请求全失败、页面一动不动」）。
  要用 `run_in_background`。
- `unit-args.mjs` 编译 `tools.ts` 要带 `--jsx react-jsx --types vite/client --lib dom`：
  它 `import type { StoreValue } from '../../state/store'` 会一路解析到 `store.tsx` → `files.ts`（有 `?url`）。
- 静态扫工具块要在 `^  },$` 处截断，否则最后一个工具会把 `renderToolList` 也吃进来（`tool.args.length` 误报）。
- 护栏插话**不渲染在界面上**，e2e 看不到 → 假上游加 `stats.marks` 数它们出现过没有。

**验证**

## 一致性检查：一次把多条问题都生成修订方案

**需求**：作者原话「一致性检查的结果如果有多个修订方案的话，提供一个全部修订至审查的方案」。
审完一遍往往不止一条问题，逐条点「生成修订方案」要点十几次。

**实现**
- **提示词**（`promptText/{zh,en}.ts`）：新增 `consistencyFixItem`（一条问题一块，字段与
  单条那条**逐字一样**，模型不用学第二种读法）与 `consistencyFixMany`（"请一并修复同一个条目上的
  下列 {n} 处……这几处的改动方向可能互相牵动，请一起考虑，不要按下葫芦浮起瓢"）。
  单条仍然走原来的 `consistencyFix`（措辞更贴合"就改这一处"）。
- **规划**（`ConsistencyPage.tsx`）：新增模块级 `fixTargetOf(issue, entries)` 与
  `planFixes(issues, entries)`。按**目标条目**分组，于是：
  ① 同一目标的多条问题合并成**一次**请求（一条条改会让后一次推翻前一次，作者拿到三份打架的方案）；
  ② 每条修订只占队列里一个位置，"同一目标不叠两份待审"这条纪律才守得住。
  `fixTargetOf` 取「第一个**还在库里**的相关条目」，不再是死取 `relatedEntryIds[0]` ——
  相关条目被删掉后旧写法会安静地什么都不做，作者点了只看到"没反应"。
- **入口**：准备就绪的组 ≥ 2 才露面（只一条时旁边卡片上的按钮就够了）。跑着时面板留着，
  显示「1/2 · 匠人同盟」+ 进度条，可中止。同时**复用 `consist.scan` 这个任务槽** ——
  审计/单条/全部本来也只允许跑一件，共用之后侧栏转圈语义才干净。
  结果经 `ai.setResult` 存进全局任务槽（不存就切走即丢，这条踩过）。
- **结果卡**分开报四种数：生成几条 / 几条问题被并进同一条修订 / 几条生成不了（相关条目在库里
  找不到，只能人来处理）/ 几条失手（可单独重试）。四件事意义完全不同，合成一句"已完成"等于没说。
- **问题标记已处理**：生成成功的那几条 `acceptReview(id, {})`（对 consistency 只是改状态，
  不写库）；生成不了的如实留在待处理里。

**踩的坑（重要）**
- **`runBatchId` 那个状态**：跑的过程中一条条推修订，而那些修订的目标正是施工图上的条目 ——
  不区分的话第二圈渲染就把它们当成"已有待审修订"，施工图越缩越小、界面上的条数一路掉。
  用 `useState` 记住本次批号、`(!runBatchId || r.batchId !== runBatchId)` 把自己产出排除掉，
  **跑完再置回 null**（否则下一轮会把上一轮自己的产出永久豁免，等于叠第二份修订）。
- **假上游的路由陷阱**：一致性分支原先靠**世界名**里的触发词分派，而世界名会出现在这个世界的
  **所有**提示词里 —— 于是同一个世界随后跑的「生成修订」（expand 提示词里也带着世界名）
  被 `consistency-many` 截胡，收到一份 issues 列表 → 产出的修订内容正好等于原文，
  看起来像"AI 一个字都没改"。修法：触发词必须**和这条任务自己的形状标记一起判**
  （`has('多修订标记') && has('"issues"')`），`畸形返回` 那条也一并收紧。
- 单条修订原先没有自己的分支，回的是通用 `EXPAND`（内容是固定示例），无法证实"发过去的是哪一条"。
  补了 `consistency-fix` 分支，把收到的问题原样写回正文；合并版同理（`expandManyPayload` 逐条回写）
  —— 「合并有没有静默丢问题」这是唯一可靠的证据，光看条数看不出来。

**验证**
- `e2e-consist.mjs` 从 **30 项扩到 57 项**（仍全绿）：新增 7~9 三段 ——
  一次审计出 6 张卡 → 横幅报「2 条问题可以一并生成」并提前说清「另有 1 条先放过」→
  点「全部」→ 进度「1/2 · 匠人同盟」→ **切页不打断、侧栏继续转、在别处跑完、切回来结果卡还在** →

  生成不了的和先放过的**如实留在待处理** → 审查页批头「同一批 · 2 条」→ 整批采纳后正文真的变了 →

- 假上游新增 `consistency-many`（五条问题：两条盯同一目标、一条落别处、一条落在已被待审修订占住的

## 功能：世界时间线（可视化添加 + 导出大事记 + agent 可读写）

用户原话：「为世界观添加时间线，可视化添加时间线显示」。落成三件事：**一域数据**（`timeline` store）、
**一条轴**（`TimelinePage.tsx`）、以及**把这一域接进既有体系**（导出 / agent / 审查 / 记忆 / 回归）。

### 数据模型（`src/types.ts`）

```ts
interface TimelineEvent {
  id; worldId; title;
  date: string;   // 世界内纪年，作者怎么写就怎么存（「涨潮纪 12 年」）
  order: number;  // 排序用数值位置；轴上的先后、间距、纪元分段全靠它
  era: string;    // 纪元名，同段连成色带；留空 = 不属于任何纪元
  weight: 'major' | 'normal' | 'minor';
  detail: string; entryIds: ID[];
  createdAt; updatedAt;
}
```

**时间是两个字段，不是一个**（这是整件事的地基）：只存文本的话，「涨潮纪 9 年」会排到「10 年」后面 ——
按字符串排序对世界内纪年根本不成立。

### 可视化添加的要害

- `orderAt(x)` 把点击的 x 反算成 order，**点击与拖动共用同一个函数**。落在两件事之间就是插进去；
  落在轴两端（ratio ≥0.98 / ≤0.02）返回 `hi+span*0.25` / `lo-span*0.25` —— 明确拉开一步，
  而不是叠在端点那件身上（早先用「两端留 7% bleed」实现，结果是点最右端只挪一点点、新点盖住末尾）。
- 落位后**面板直接停在编辑态、光标已在事件名上**（`wantFocus` + 一个 `useEffect`），
  省掉「新建一条 → 再点开它」两步。
- 表单**失焦才落库**且无改不写（`commitForm` 逐字段 diff）；输入即时进 state，用 `formRef` 双写
  防止闭包旧值覆盖刚打的字。

### 其余交互

纪元色带 + 图例筛选；事件分三级（节点大小不同，重大的名字一直露着）；
两档轴距「按年代比例 / 均匀铺开」**只改画法、不动 `order`**；疏密缩放 `ZOOMS=[1,1.5,2.5]`；
关联多个条目；删除与操作日志撤销。

**摆位（改过一版）**：一开始按「画出来的 x 每 30px 一桶」分槽，同桶的上下让开。
五件挨得不远的事件摆上去，节点是分开了，**名字却压在一起** —— 名字有十几个字宽，
相隔 68px 的节点照样叠字，叠着的字比叠着的两个点更糟（点至少数得出来）。
改成**按标签估算宽度做首次适配**（`labelWidth()`：汉字 ≈11.5px、其余 ≈6.2px）：
从轴往上、往下依次找第一条放得下的槽，最多让到 `MAX_LANES=6`（再深就压到底部那条添加带）。
参与占位的只有默认会显示名字的节点（重大 / 一般）—— 悬停与选中是临时的，
拿它们算分槽会让鼠标一划过整条轴就跳。配套给 e2e 加了一条用 `getBBox()` 的两两相交断言
（「轴上的事件名没有互相压字」），这条毛病就是它抓出来的。

### 接进既有体系

- **导出**（`src/lib/export.ts`）：`ExportOptions.includeTimeline`，Markdown 里多一章「大事记」。
  最初按纪元 `filter` 分组 → 历史顺序被打乱，被自己的断言抓住（`idx` 必须递增）。
  改成**按 `order` 遍历、纪元换段时才开小节**：小节是阅读的辅助，先后才是这件事的本体。
- **agent**：`list_timeline`（读，空时间线单独一句「时间线上还一件都没有」，别用「没有找到匹配的内容」
  误导它以为是查询没命中）+ `propose_timeline_event`（写，进审查队列；`timelineDraft`）。
  `propose()` 的日志实体按 kind 分流（timeline-event → `timeline`），`acceptReview` 里
  按 `timelineDraft` 造事件（`order` 缺省落末尾，`entryIds` 过滤掉已删条目）。
  提示词加了 `agent.sys.timeline`：**动笔之前先看一眼时间线上已经有什么**，年代照作者原文抄、
  不许换算公历，只有真正改天换地的才标 major。`navigate` 的页面清单补 `timeline`。
- **审查页**：`kind-filter` 补「大事记事件」；卡片显示纪年 / 纪元 / 分量 / 详情 / 关联条目，
  并明说「采纳后落在时间线末尾，位置可以在时间线页上拖」+ 一个「去时间线看看」的入口。
  顺手给卡片驳回按钮补了 `data-role="review-reject"`（此前只能靠文案选元素）。
- **其它**：`OpEntity`/`ENTITY_FILTERS` 补 `timeline`；DB_VERSION 4→5，所有 `.dev/*.mjs` 同步升版。

### 踩的坑

- **`el.blur()` 在无头 Chrome 里什么都不会发生**（文档没有焦点，浏览器直接跳过），
  自造的 `new Event('blur')` 也不顶用 → 「打字没写进库」是假失败。改成派发
  `new FocusEvent('focusout', { bubbles: true })`（textarea 用 `HTMLTextAreaElement.prototype` 的 setter）。
  真人按 Tab/点别处时浏览器发的正是 focusout —— 不是产品的问题。
- **拖动没生效**：mousemove/mouseup 监听经 `useEffect([dragging])` 挂载，比 `mousedown` 晚一个渲染周期，
  按下后立即的位移落在监听未挂的空隙里。改成在 `onMouseDown` 里**就地** `addEventListener`、
  松手 `removeEventListener`。

## 功能：右下角的任务队列（连点好几下 = 排好几件）

用户原话：「在检查中的审计用ai润色的时候可以一下子按好多个进行队列等待，而且不止这些，
其他甚至未来都可以采用这个队列，在右下角作为提示」。落成三件事：**一层通用队列**（`state/jobQueue.ts`）、
**右下角那枚胶囊**（`components/TaskDock.tsx`）、**把两处「一次想点好几下」的活儿接进去**
（一致性检查逐条生成修订、条目列表逐行 AI 打磨）。

### 它到底修了什么

原先这类单发动作各自调 `useAITask(key).run()`，而那个 `run()` 有一条刻意的纪律：
**同一个 key 还跑着就直接返回 `null`**（防止两发结果互相覆盖）。单发场景下它是对的，
可作者手快连点三条时，后两条就**静默消失**了 —— 按钮闪一下、什么都没发生、也没有任何交代。
那不是「慢」，是「按了没反应」，比报错更让人不放心。

于是把两层拆开：
- `useAITask` 继续管「一个页面上一件大事」的流式状态（进度、流式预览、结果卡）；
- **`jobQueue`** 管「一堆小活儿，排队慢慢做」：点一下加一件、点十下加十件，串行地一件件跑完。

### 设计要点

- **串行 `CONCURRENCY=1`，不并发**：AI 按量计费；并发多半撞上游的速率限制反而更慢；更要紧的是
  **写库顺序会乱**（两件同时改世界谁先落盘说不准），而作者点下去的顺序本身就是他的意图表达。
- **跑法单独放一个 `Map`**（`runners`），不进给 React 的快照 —— 快照必须是可稳定比较的值。
  `useSyncExternalStore` 的 `getSnapshot()` 返回同一个模块级数组，只在 `notify()` 时重建一次。
- **失败不堵队列**：一件烂了记下错误继续下一件（卡住整条队伍会让后面那些能成的陪着死）；
  失败的**保留跑法**以便原地重试，跑完的立刻丢掉（它闭包着一份当时的快照，留着白占内存）。
- **入队去重**：`dedupeKey` 只跟**还活着**（排队/正在跑）的那件比。跑完的再点一次是有意义的，
  该不该拦是调用方的事。
- **世界隔离**：跑着的照显（不然切了世界就撤不掉单）、别的世界跑完的不显（否则是上一个世界飘来的垃圾）。
- **热更新兜底**：`import.meta.hot.dispose` 里清表并 abort 掉在跑的 —— 否则改一行代码热替换后，
  上一轮「正在跑」那件会永远停在那儿（它的 promise 随旧模块没了）。

### 那枚胶囊

收起态写「正在为《匠人同盟》生成修订方案，后面还有 2 件」，跑完变绿（「队列已清空 · 共完成 3 件」）、
有失败变红（「1 件没做成」）；展开是清单：每件叫什么、排队中/正在做、已跑几秒、失败原因、撤单 / 重试。
`z-index: 210` —— 高过模态框，改条目时也看得见、撤得掉。

### 两处活儿怎么接进去

- **一致性检查**：`generateFix` 从「跑一件」改成「入一件队」，`label` 是「为《X》生成修订方案」。
  去重键 `consist-fix:<条目id>:<问题id>` —— **键里塞了两件事**：条目 id 用来守「同一条条目一次只改一份」
  （与「全部生成修订方案」把同一条目上的多条问题合并成一条是同一条纪律），问题 id 用来点亮对应那张卡
  （同一条条目上的第二条问题不该跟着一起转圈）。被挡下的那一下**明说为什么**并指向批量入口。
  顺手删掉了老代码里的 `fixingId` 局部状态（那本来就该是队列状态的投影）。
- **条目列表**：每行多一颗「AI 打磨」（`data-role=entry-polish`），复用批量面板那套提示词与 `focus`/`extra`。
  批量模式下这颗按钮让位（整行那时归勾选，两种点击语义不能打架）。单条打磨**不挂批号** ——
  它是「这条我看不顺眼，改一下」，要成群处理就去用批量面板，那里才有「采纳这一批」的意义。

### 顺手做的一件事

把「AI 配置填全了没有」抽成 `aiGuardKey(ai)`（`state/aiTasks.ts` 里导出），三处共用：
`useAITask.run`、入队之前、以及工作台里那个静默判断。各写一份的话迟早出现「这边放行、那边拦下」。

### 踩的坑（已写进 MEMORY.md 铁律 42~47）

- **做判断不能读 React 快照。** 第一版用 `useJobs()` 派生的 `targetIds` 去判「这条条目是不是已经在排队」，
  结果一口气连点 4 下**排上了 4 件**（同一条条目的两份修订同时在路上）。原因：4 下全部发生在
  React 重渲染**之前**，快照里一件都还没排上。修法：新增 `hasLiveJobPrefix()` 直读模块内的表 ——
  **做判断读队列本身，显示才读快照**。
- **闭包里的 `store` 会过期。** 队列里的活儿是过一会儿才跑的，那期间库可能已经变了。
  读（世界/条目/分类）继续用入队时的快照（那是作者的意图），写（`pushReview` / `acceptReview`）
  改用 `liveStore = useRef(store)` 指向的最新那份。
- **e2e 读「展开才渲染的面板」之前必须先展开**：收起时那些行不在 DOM 里，直接读得到空串，
  断言会以「什么都没排上」的形状失败（典型的假阴性）。让 `dockJobs()` 自己先确保面板是开的。
- **假上游不发 CORS 头是设计内路径**：应用直连被浏览器拦下 → 自动改走 `/__wf-proxy`。
  于是每次 AI 调用都在控制台留两条 CORS 报错，「没有 error 级日志」这条断言必须按
  `blocked by CORS policy|net::ERR_FAILED` + mock host 白名单放行（`e2e-consist` / `e2e-polish` 早就这么做了）。
- 断言写错过两次，都是**对真实行为理解不到位**而不是代码错：按钮是 **4** 个（两条问题盯同一条条目，
  各有一个按钮）但点 4 下只排上 3 件；打磨请求是 **4** 次而不是 5 次 —— 因为被撤单的那件
  **一个请求都没发出去**（这正好是要验的东西，改成断言「正好四次（撤掉的那件一次都没发出去）」更有价值）。

## 28. 解析层：把它「写歪了但东西都在」的输出按结构救回来

起因是作者贴回来的一次**真实翻车**：他让 agent 补一批条目，模型一次给了 8 个 `create_entry`，
界面上却连续两轮说「它这次没按约定的格式回，已请它重说一遍」，8 条写好的提议被扔掉两次；
第三轮只补了一条，中间还把「年轻法师的导师」重复建了一次（被「库里已经有了」拦下）。
也就是：**模型给动作了，应用一个都没执行。**

### 先定位，不猜

把那次模型原话**逐字**存成 `.dev/tmp-raw1.txt` 灌进解析器：`protocolBroken = true`、`plan = 0`。
裸 `JSON.parse` 报 `Expected double-quoted property name in JSON at position 687`。数括号：
**17 个 `{`、只有 9 个 `}`** —— 8 个动作对象**每个都少写一个收尾的 `}`**（`args` 关上了、动作自己没关）。

前面那几手救援一个都够不着它：末尾逗号修不掉；`closeTruncated` 只会往**末尾**补括号，
少在**中间**的东西它看不见。于是作者看到的就是「它说完了，然后什么都没发生」。

### 改了什么

- **`looseJson`：逐 token 结构修复**（`src/ai/parse.ts`）。撞见不该出现的 token —— 最典型的是
  在「该写键名」的地方撞见 `{` —— 就地补一个 `}` 把当前这层收掉，**再拿同一个 token 到外层重试**。
  补 `}` 之前先把紧挨着的那个逗号撤掉（否则得到 `{… ,}` 这种非法形状）。
  守门三条：先粗判「像 JSON」（有带引号的键 + 冒号）；改动次数超过 `min(64, 字符数/8)` 就返回
  `undefined`；修完真能 `JSON.parse` 出东西 —— 宁可让调用方报错，也不许把随笔「修」成空对象。
- **顺带修掉一个更隐蔽的缺陷：次序。** 老逻辑「从最后一个逗号切下去、切出来的前缀只要能解析就算数」
  是**有损**的：同一份 8 动作输出被它切到只剩 1 个，**还报告成功**。这正好解释作者另一句
  「它根本就没补全」。改法是 `closeTruncated` 返回 `truncated` 标志，**只在真截断时才切尾**；
  结尾是收尾括号就先走结构修复。
- **全角归一**：`｛｝［］：` 走 `FULLWIDTH` 映射 + `at(k)` 访问器，只在**结构判断**处按半角看待，
  字符串内容一个字不改；引号的全角变体不认（猜错了不如老实说读不懂）。
  单独先试一遍全角是因为 `extractJson` 那句「截取第一个 `{` 到最后一个 `}`」在 `｛"say":…`
  上会从 plan 的 ASCII `[` 起截，截出一个「只有动作」的合法数组、把 `say` 丢掉。
- **`extractJsonEx` 返回 `{ value, loose }`**，`extractJson` 退化成薄包装 —— 修复这件事
  必须能被上层看见，不能被吞掉。
- **界面三态**：`ChatTurn.protocolBroken?: 'retried' | 'gaveUp' | 'repaired'`、
  `AgentReply.salvaged`。`repaired` 用中性色（黄留给「这一轮真的废了」），
  文案点明是括号问题：「它这次 JSON 写得不合规矩（有几个地方少写了括号），我按结构补齐了 ——
  动作一个没少，照常往下走。」**修复 ≠ 放过**：提议照旧进审查队列。
- **提示词侧堵因**：工具清单里明写「每个动作是两层、结尾要有两个花括号」；一轮从「最多 8 个」
  改成「最多 8 个 —— 但建议 3~5 个：动作越多、每件内容越长，JSON 越容易写坏」；
  纠错轮加一句「要是写到一半就断了，这一轮就少做几件（比如先建 3 条）」。

### 踩的坑

- **结构修复只吃第一个值**，撞上「模型吐了两个并列 JSON 对象」那个老场景就漏了第二块 →
  `parseAgentReply` 里 `if (salvaged)` 时用 `jsonChunks(text)` 复查，块数 > 1 就换成分块结果。
- **假上游「两个动作各少一个括号」的回包只救回 1 条**：切尾仍排在结构修复前面，先切出一个
  「只有第一个动作」的合法前缀就返回了。调整次序后 `plan = 2`。
- **提示词模板串里不能用未转义的反引号**（`` ` ``），`tsc` 会报一串 `TS1005`；
  改用「花括号」这种说法。
- **i18n 覆盖率把 `ch === '｝'` 当成硬编码中文文案报了 11 处** → 抽成 `FULLWIDTH` 映射表
  （只在该行加一个 `// i18n-allow`），覆盖率回到 0 残留。

## 关系图谱的可读性：圆的轻重跟着联系走

### 用户要什么

> "如果条目过多，关系图谱可读性会变差，我希望优化一下，譬如透明度渐变，随着联系变大圆也变大"

现状确实糊：**所有节点一律 `r=11`、一律 `opacity=1`、标签一律纯黑**。几十条条目摆上去，
枢纽和边角长得一模一样 —— 等于没画关系。用户给的两个例子（透明度渐变、圆随连接数变大）
正好抓住了该做的两件事。

### 刻度：大小开方、深浅不压缩（这两个量刻意不同）

`weightOf(degree, maxDegree)` 一次生出两个刻度，注释里写清了为什么不一样：

- **半径**用 `sqrt(deg/maxDeg)`。真实关系网是长尾的：少数枢纽牵着十几条线，大多数只有一两条。
  照原值铺，枢纽一格就把刻度吃光，其余全糊在最小档 —— 开方才把中段拉开（「两条 vs 四条」看得出来）。
- **透明度**直接用 `deg/maxDeg`，**不压缩**。透明度要的就是「长尾退下去」，压缩反而让边角抢戏。
  名字同理（`lo = 0.16 + 0.84*t`，字号 `9.5 + 2.5*sqrt`），边角最后几乎只剩一个点。

一个世界一条关系都没有时没有「轻重」可言 → `maxDeg <= 0` 一律给中档 0.55，别排座次。

### 最要紧的一条：「敢压多暗」得跟着稀疏稠密走

第一版直接把下限写死成 `O_MIN = 0.34`，然后在 12 个点的稀疏图上目测 —— 那会把好好一张图看糊。
所以加了 `density = clamp((n - 14) / 46, 0, 1)`，下限随之插值：**稀疏时谁也不压，稠密时才让长尾退到底**。
数的是**眼前这张图**的连线（被藏的分类、关掉的待定关系都不算 —— 看不见的关系不该让圆变大）。

配套还顺手做了三件：
- **选中即聚光**：`litIds` = 它自己 + 直接相连的一圈，邻居名字强制读清，无关的退到 0.3 倍。
  顺带把 `dim` 的算法换了：原来是**每个节点各扫一遍连线表**（O(节点×连线)，60 个点就是每帧 800+ 次比较），
  现在先扫出一圈集合再查表 —— 条目一多，这正是不该浪费的地方。
- **连线的类型文字也压淡**（`1 - 0.5*density`）：线一多，「关联」两个字先糊成一片。
- 右上**「按联系轻重」开关**（默认开）+ 图例末尾一个三圆示意 —— 想平着看就退回从前的样子。

### 又抓到一个真 bug：函数式更新

e2e 里「一口气点两个图例分类」，结果只藏住了一个。根因：
```tsx
onClick={() => { const next = new Set(hiddenCats); … setHiddenCats(next); }}
```
`hiddenCats` 是**渲染期闭包**里的那份 —— 同一 tick 里连点两次，两次读的是同一份旧集合，
后一次把前一次覆盖掉。真人手点两次是两个 task、中间会 flush，所以平时看不出来。
改成 `setHiddenCats((prev) => …)` 即可。和铁律 56（store 读最新快照）是同一类病：**闭包里的旧快照**。

### 测试

`e2e-graph.mjs` 41 → **58 项**，新增第 12 节：铺一张密图（1 个枢纽 13 条线 + 12 个从属 + 50 个长尾，
共 66 条），从 DOM 读回每个节点的 `r` / `opacity` / 名字透明度 / 字号，断言
`枢纽 17.0 / 从属 10.5 / 孤立 8.0`、`1.00 / 0.39 / 0.34`、`1.00@12px / 0.16@9.5px`；
选中枢纽后从属名字 `0.22 → 1.00`、孤立点 `0.34 → 0.102`；关掉刻度后 `11 ~ 11`、名字一律 1；
再藏掉两批分类 → 只剩三个点、**透明度全回到 1.00**（稀疏不压暗）而半径仍有 17.0 / 14.4 两档。
节点组上加了 `data-degree`、圆点与名字加了 `data-role`，刻度才读得出来。

写这一节时还踩了个小坑：**选中是在 `mouseup` 上落地的**（`mousedown` 只是开始拖，没拖才算单击），
只发 mousedown 什么都不会发生 —— 库里现成的 e2e 就是这么写的（mousedown + window mouseup）。

## 一致性审计：从「每次都报同一批」到带着账本出去（作者原话）

  「换个说法也算重复」。`consistencySystem` 的纪律从 3 条加到 6 条（新增「账本压过直觉」、
  「可重看是唯一例外」、「一条新的都没有就返回空列表，这是正常结果不是失败」）。
- **「可重看」用时间戳判，不靠模型**：`entry.updatedAt > issue.createdAt`。
  代码算好再告诉模型 —— 让它自己去比时间戳只会瞎猜。顺带自洽兜住误点忽略。
- 入库前再拦一道（`splitDuplicates`），拦下的**点名报出来**。判重只认字面级：
  归一后相同，或一个套着另一个。
- 提示词里如实写「本次送入」：索引列出几条（另有几条不在索引里）、正文每条最多多少字，
  以及一句「条目越多，每条正文分到的越少 —— 别把『我没看到』当成『没问题』」。
- 页面：审计结果卡（新增几条 / 拦下几条 / 账本还压着几条）、列表默认**只看待处理**
  （判过的折进「全部」）、范围横幅说实话、空了区分「还没有审计记录」与「待处理清空了」。
- 新增 `consist.toast.foundNothingNew`：账本非空但没新问题时**不能**沿用「没有发现明显的设定冲突」
  —— 那是「一次判断」，这里的实情是「该报的都报过了」，说成一句会让作者以为设定干净了。

### 为什么判重做得这么保守（量过的）

试过追「换个说法」，追不动：同一条问题的两种说法（「烬石储量与城邦规模不匹配」/
「烬石产量撑不起城邦规模」）余弦相似度只有 **0.38**，而同一批条目上两条**不相干**的问题

## 时间视图大改：从「填表」改成「放置」（作者原话）

> 「时间线不是我想象中的时间线啊，大改一下吧，我的目的是最初类似视图一样的页面，能将各个事件

> 而不是还需要我手动设置（也可以手动设置进行更细致的规划，但是现在这个版本太麻烦了）」
>
> 「而且之前改的能将条目关联时间也和我想象不一样，这还是删掉这个功能吧」

两句话连起来读，是**两件事**：① 主入口错了 —— 我把时间轴做成了「填表」（点轴上一点 → 开编辑器 →
填起止/纪元/分量），作者要的是**一个画布**：把条目**放进去**，轴自己成形成；② 上一轮我加在轴上的
「连到别的条目」（`time.link.*` / `linkBetween` / 连线模式）他压根没想要，**整块撤掉**。

### 改了什么

- **删**：`TimeAxis.tsx` 里的 `linkFrom` / `relType` / `query` / `linkBetween` / `relOf` / `relTypes` /
  `hits` 全部状态与逻辑、`tl-link-banner` 横幅、节点上的 `tl-link-source` / `tl-link-target` 圈、

  按分类 order + 标题排，可打字搜（标题/别名/标签）。**拖一条到轴上任意一处即落位**
  —— 位置由落点 x 反算（落在两条之间就是插进去，落在两端就是拉开一步）。不想拖就
  **点一下条目（挂起）、再点轴上任意一处**，走同一个 `placeAt(id, at)`（铁律 67）。
- **加（诚实）**：落位**只写 `at`、不编 `from`**（铁律 69）。拖进来的是「位置定了、说法还没写」，
  节点画**虚线圈** `data-notime="1"`，图例写「虚线圈 = 位置定了，时间文字还没写」。
  道理：作者没说这是哪一年，代码没资格替他编一个。

  （`input` 与 `focusout` 可能在同一任务里连着来）。写库仍只有 `store.setEntryTime` 一处。
- **加（空态）**：轴**永远渲染**（不再 `if (!all.length) return <Empty/>` 提前返回）。
  空轴中央一行 `data-role="tl-axis-hint"`「把右边的条目拖到这条轴上」，空态卡片挪到轴**下方**
  （铁律 70）—— 空轴是**落点**，不是「暂无数据」。

### 两个真坑

1. **`movedRef` 把 click 永久吃掉（真 bug，不是测试问题）。** 池子行既要「点」又要「拖」，
   原写法在 `mousedown` 记 `movedRef`、`mousemove` 置 true、`click` 见 true 就忽略。
   结果「拖到轴上松手」之后 `movedRef` 一直挂着，**下一次真点击也被当成「刚拖过」**。
   修法：把判别**搬进 `mouseup` 那一刻一次判完**（落在轴上 → 落位；没落在轴上且指针没动过 → 挂起），
   `onClick` 只处理 `e.detail === 0`（键盘）。→ 铁律 68。
2. **同步 evaluate 里读 DOM = 必然假红。** `mousedown` + `mousemove` + 读 `tl-carry` / 幽灵线
   全塞在同一个 evaluate，React 还没提交这一帧 → 读到上一帧的元素。拆成
   「按下 / 移动 / 读 DOM / 松手」四次 evaluate，中间各 sleep。→ 铁律 71。
   顺带：`evaluate` 抛错时**把出错那句表达式原样打出来**（我写选择器少了个 `')`，
   只看 `missing ) after argument list` 只能靠猜；打印原文后一眼就看见了）。

#### 中途插曲：onboarding 连红两次，凶手不是时间轴

第一遍全量跑下来 `e2e-onboarding` 红了一片（「问题 0 个 / 草案 0 条」），
位置在**第 1 步「让 AI 读一遍」** —— 和时间轴改造八竿子打不着，但不能放过。

排查路径（值得记，因为它差点把锅扣到重构头上）：
1. 先证明它可复现（单独重跑，红在同一个点）。
2. 再证明**不是我的改动**：把假上游换到另一个端口跑同一份 `dist`（`e2e-onboarding.mjs` 的第 2 个
   参数就是假上游地址），59/59 全绿。
3. 对比两个假上游的唯一差别：**共享进程上的 `/__mock-delay`**。原那个残留着 900ms
   （`e2e-queue.mjs` 设了却从不还原），新的那个是 0。
4. 做因果确认：把新假上游也设成 `?ms=900` → 同一批红复现；设回 0 → 全绿。

机理：回包慢下来之后，「正在跑」的**转圈卡片**（也带 `ob-card` 类）被
`waitFor('document.querySelectorAll(".ob-card").length >= 1')` 抢先命中 ——
「AI 给出了它读懂什么」判 ✓，可里面的正文还是空的，后面十几条断言跟着塌。
**平时一直是绿的，因为瞬时回包时转圈卡在下一次轮询前就被结果卡换掉了。**

三处都修了：
- `e2e-queue.mjs` 收尾 `?ms=0`（它是唯一一个自己设了却不还原的）；
- `e2e-onboarding.mjs` 开跑前连带 `?ms=0` 一起归零（不需要延迟的脚本也该显式声明），
  并换了初始化的字段 —— 写进铁律 72；
- 那条弱断言改成**等正文真的到了**（`textContent.trim().length > 40`）。

改完在**脏环境**（原假上游仍停在 900ms）里复跑：59/59 全绿，并且它自己把延迟归了零。

日志：`.dev/mock-upstream.mjs` 每个请求都会打一行 `branch=… round=… bytes=… delay=…`，
排查这类「顺序性假失败」时**用后台任务另起一个带日志的假上游**（默认那个没有 stdout），
再拿 `e2e-onboarding.mjs <APP_URL> <MOCK_URL>` 指过去 —— 这一手比反复猜快得多。

## 时间轴的「AI 自动排版」：进队列 + 进审查（作者原话）

> 「给时间轴支持ai自动排版 要求进审查，进队列」

**纪律与 `ConsistencyPage` 完全对齐**：AI 只提议、方案先落审查、这一动作本身是入队动作。

### 判断

- **一次排版 = 一条提议，不是 N 条。** 新增 `ReviewKind = 'timeline-layout'`，
  整张方案放 `ReviewItem.layoutDraft: TimeLayoutItem[]`。拆成 N 条 `update-entry`
  看着更"统一"，实际丢了**这几条之间的先后**这层意思 —— 而作者要审的恰恰是"这一整套顺序"。
  这也是 `acceptReview` 里唯一一个**循环调 `setEntryTime`** 的分支（逐条走唯一写入口 → 各留撤销），
  同时 `logAccept` 对该 kind **早返回**：逐条已经各留一条「修改了条目「X」」，
  再叠一条汇总就是一条什么都退不回去的假账。
- **AI 只写位置。** 方案里能写回的是 `at` / `toAt` / `era` / `weight`；
  `from` / `to` 一个字不动 —— 作者还没说这是哪一年，AI 没资格替他编。
  所以「池子里那条被排进轴」落地后照样是**虚线圈**（接上一轮的铁律 69）。
- **两处对账。** 任务内对一次（模型输出 vs 送进去的快照：位置没变的不列、标题对不上进 `unmatched`），
  入队闭包落库前再对一次（`liveStore.current` vs 排队期间的当下库：删掉的跳过）。
  入队闭包里的 `store` 是点下去那一刻的（**读**用它，也应该用它），**写**必须打在当下那份库上。
- **零改动就说人话。** 一处都没变时说「现在的顺序已经对了」，而不是摆一份一模一样的空方案。
  另一半：`requireList` 取不到列表时**不许退化成空数组** —— 空数组在这里等于"它认为现在这样就对"，

## 工作台 agent：立账、能重试、不许半路收工

作者贴了他自己那一趟的完整对话：让 agent「把条目描述里出现、但还没建条目的人物和物品补全」，
结果四处翻车 —— 20 个条目只读了 3 个就说「接下来我将继续检查其他条目……」然后没有任何下一轮；
说「其他人物和物品已经在库中存在」是凭空断言；把「物品」当**分类名**撞了三次后自己新建了一个「物品」分类；
分类建好后再提同样三条，得到「这一步已经做过了，结果一样 → 不重复执行」，
于是它对作者宣称「这些条目的创建请求已经在审查队列中了」——而队列里一条都没有。
他的要求是「实现类似 Cursor / Codex / WorkBuddy 那样的 agent」。这一轮就是把那四个症状
逐个变成可验证的机制。

### 协议：清单与显式收工

- `types.ts`：`AgentTodoItem { text, done }`；`ChatThread.todos`（挂在**会话**上，切页/刷新都在）；
  `ChatTurn.todoLeft` / `promised`（两种「没做完」要分开标）。
- `protocol.ts`：`PLAN_KEYS` **摘掉** `todo/todos`，新增 `TODO_KEYS` / `DONE_KEYS` / `TODO_*_KEYS`；
  `readBool` / `cleanTodoText`（Markdown 复选框 `- [x]`、`✓`、`1.` 都读出来）/ `toTodo` / `toTodos`；
  `collect()` 的关键分岔：`todos` 里**每一条都长得像动作**就按动作读，否则按清单读
  （认错的代价不对称：把动作当清单这一轮白跑，把清单当动作只是一串「没有这个工具」）。
- **改掉了一条自己写错的前提**：原先 `todosGiven = !hasPlan && todosExplicit`（「同一轮里既给动作
  又动清单不该发生」）。那条是错的 —— 真实 agent 的常态就是**同一轮先立账、再动手**
  （「一共 5 条，我先把账立起来，现在读前 2 条」）；忽略清单的代价是那份账永远立不起来，
  而且模型下一轮回来也看不见自己刚才说过什么。改成 `todosGiven = todosExplicit`，
  `done` 仍是 `hasPlan ? false : done`。

### 循环（`useAgent.ts`）

  → **承诺没兑现**（说破一次 → 再犯标 `promised`）。
- `signatures` 从 `Set<string>` 改成 `Map<string, { summary, rev }>` + `worldRev`：
  **只拦成功过的**、**写操作作废之前的签名**、拦下时回执**引出上一次的真实结果**（`{prev}`）。

## 答完给下一步，而且记得上一句

### 跨轮记忆：每次发问都该是「接着聊」

### 晚些：接入厂商这一层做细（型号 / 采样 / 高级透传）

作者诉求：「接入的 api 能够获得更细致的配置，比如说自由选择型号，而不是像现在这样只有固定的模型，
明明模型那么多型号」。确认边界时选了「三层全要」：
①模型 ②采样参数 ③高级透传（自定义请求头 / 额外请求体）。

**病根**：型号候选是 `providers.ts` 里写死的一小段数组（OpenAI 三个、DeepSeek 两个，还都是老型号），
而且切厂商会把型号直接覆盖成 `fallbackModels[0]`，切回来自己挑的就没了。

**做法**
- `providers.ts`：`models` → `fallbackModels`（降级为**兜底**，只在还没取到列表时用）；
  新增 12 家 OpenAI 兼容服务商（火山方舟、腾讯混元、百度千帆、阶跃星辰、零一万物、OpenRouter、
  Gemini、xAI、Groq、Mistral、302.AI、LM Studio），按「常用 / 聚合与海外 / 本机」用 `<optgroup>` 分组。
  baseUrl 全部有出处（聚合站互相矛盾的那几家如 MiniMax，宁可不写）。
  新增纯函数 `switchProvider` / `urlOverridden` / `rememberModel`。
- `src/ai/models.ts`（新）：`parseModelList`（认 `{data}`/`{models}`/`{model_list}`/裸数组，
  条目认字符串与 `{id|model|name|model_id}`）、`sortModels`（对话在前 + `created` 新的在前 + 稳定）、
  `matchModel`（多词全命中）、`buildChoices`（最近/拉到的/内置三组，去重、搜索时不摆「最近用过」）、
  `fetchModels` + 本机缓存（`worldforge:models:<provider>@<baseUrl>`）。
  明显非对话的（向量/语音/画图）**标一句挪后面，不藏**。
- `client.ts`：抽出 `parseExtraObject` / `readExtras` / `mergeHeaders` / `shouldStream` / `buildChatBody` /
  `apiRequest`（GET 也走同一套「直连→本机转发」）。新增生效项：`maxTokens`、`topP`、`stream`、
  `jsonMode`（三态 `auto|always|never`）、`extraHeaders`、`extraBody`。关掉流式时**拿到全文补一次回调**。
- `src/components/ModelPicker.tsx`（新）：输入框永远可手填 + 可搜索面板 + 「获取模型列表」+ 三组候选
  + 来源标记 + 「上次获取：X 前」。打开面板自动拉一次（有缓存就不拉）。
- `SettingsPage`：型号换成 ModelPicker；新增 token 上限 / top_p / 流式开关 / 高级折叠区
  （JSON 模式 + 两栏 JSON，**就地报红**）；地址被改过时摆「恢复官方地址」。

**过程中逼出来的两个真缺陷**
1. 把某家预设的地址改成中转站后，切走再切回来地址被还原成官方的（`baseUrlByProvider` 修掉，
   只记「和官方不一样」的，并给「恢复官方地址」）。
2. **本机转发器把额外请求头丢了** —— `tools/local-proxy.mjs` 原先把头重建为四个，
   于是同一个配置直连能用、一退回转发就没了，厂商只回一句「参数不对」。
   改成「滤掉浏览器自带的与逐跳头，其余原样转发」。这条是 e2e 在**不加 `--cors`** 的那趟里红的。

**测试**：新增 `.dev/unit-ai-config.mjs`（102 项，九节）+ `.dev/e2e-ai-config.mjs`（58 项，十四节）。
假上游新增 `GET /v1/models`（五种形状模式）、`stats.modelsFetched` / `chatCount` / `lastBody` /
`lastHeaders` / `lastMessageCount`，控制端点改用始终带 CORS 的 `CONTROL_CORS`。
回归：typecheck ✓、i18n-coverage 58 文件 ✓、七个单测 30/21/31/56/56/4/102 ✓、十六个 e2e ✓、sweep ✓。

**踩坑**：①`--strict` 缺一个，联合类型收窄失效，四个单测脚本编译不过而报错长在 `client.ts` 上；
②那几个脚本的汇总行格式不一，批量 grep 窄了会把「通过」看成「无结果行」；
③`.banner.info` 在设置页选择器太宽（选中了「存储」那块横幅），统计读早了 —— 改用
`stats.chatCount` 等「厂商真的收到」；
④断言里用了刚被选中、已挪进「最近用过」组的型号（去重是对的，断言错了）。
